# Project rules

## Contract–implementation co-evolution

Every section of a behavioral contract must agree with the rest: any input surface or requirement declared up front is actually consumed by the algorithm under the declared resolution order, and when the algorithm is corrected, the companion design trace and its derived tests are updated in the same change so no artifact describes a different behavior. User-visible behavior is pinned across the implementation, the command and rendering code, the contract manifests, the usage files, the user documentation, and the tests, so a change to a cell's public surface or value domain propagates in that same change to every layer and artifact describing that surface — design traces and algorithm steps, aggregate export counts, import lists, test mocks, and usage documentation — with contract validation re-run after each edit, the repository swept for residual old wording, and lint left clean, so no specification drift remains; updated test expectations are part of the contract change rather than regressions. This propagation is the definition of done: a change to behavior or wording is complete only when every layer describing it is updated to the new state within the same change, pre-existing stale descriptions encountered in touched files are corrected rather than preserved, and finishedness is verified by repo-wide sweeps for leftover old wording plus the project's lint checks before the change is declared complete. Value domains and marker vocabularies are drawn from the project's own lifecycle vocabulary: they are action-oriented so a display tells the user what to do next, single-token kebab-case with no aliases or alternate spellings, and a superseded token is retired from the domain entirely rather than kept as a synonym. The sweep covers prose as well as executable code — a ban on a removed mechanism extends to docstrings and comments, and stale documentation that still describes the removed channel is rewritten even in modules whose code never used it, so later readers are not misled. All interaction with an external tool goes exclusively through its owning cell's declared contract: a missing capability is added as a declared routine in that contract and consumed through it, never obtained by bypassing the boundary with direct tool invocations or semantically distorted workarounds. Where the contract grammar cannot express a default that existing call sites still rely on, the default belongs in the implementation-language signature, and the design document states unambiguously which layer carries it, so callers that omit the argument keep working unchanged. Production code stays exactly within its declared contract: a failure caused by an unmet environmental precondition surfaces as a clean error and is repaired on the caller's-side, never absorbed by hardening production beyond what the specification promises. When a defect surfaces at a contract boundary, fix the implementation to satisfy the existing specification and amend the specification only to state the boundary explicitly, then confirm consistency through the project's specification validation gates; never rewrite the specification to legitimize buggy behavior, because altering a specified guarantee is breaking drift. When instead the implementation agrees with its contract yet the observable behavior is wrong, the defect is contractual rather than an implementation slip: the fix redefines the guaranteed behavior in the contract itself instead of correcting only the code and leaving the specification pinning the wrong rule.

## Grounded, hermetic, complete, and honest verification

Throwaway test repositories built by a fixture are provisioned at creation time with every piece of configuration their scenarios can reach, so outcomes never depend on ambient host or runner state; the reason is documented in the fixture and follows existing precedent fixtures. Expected values are themselves grounded before they are written: semantics borrowed from external dependencies and the behavior of designed algorithms are established live, via small probe runs against the installed dependency and direct simulation of the algorithm, and the expected outcomes of domain algorithms are derived from the domain's actual rules — eligibility preconditions, priority order, and the canonical ordering scale including its direction — with fixtures constructed from inputs that genuinely satisfy those preconditions, so every expected result is one the real algorithm can produce; recollection of how something should behave is not an acceptable basis, and existing pinned tests serve as the reference for rule direction. Assertions mirror the semantics of the exact code path under test rather than a sibling path: expected call counts and effects are derived from what that path actually performs, so a test never freezes wrong semantics or forces behavior the algorithm does not have. Mock–assertion parity binds every repair that introduces a mock for a guard or boundary: the test's assertions must explicitly prove the strengthened property for every invocation, including the full expected interaction order, instead of silently absorbing the mocked call — the repaired test must be strictly stronger than the one it replaces, and that strengthening is stated when the fix is planned. A passing suite is still not proof of correct semantics when the expectations themselves pin the wrong behavior: correcting the behavior requires rewriting those enshrined expectations and adding inverse cases at every test level, never preserving them merely because they pass. When the conflict runs the other way and a scenario's expected value disagrees with its own setup, the setup is extended so the case still exercises its intended behavior and the expectation stays meaningful; the expectation is never weakened to the accidentally-passing value, nor is the implementation's contract rewritten to match a mis-written test, because both silently delete the case's intent. When a verification probe fails partway, the probe itself is repaired and re-run, preserving results already verified, rather than continuing on unverified assumptions. Validate on the environments where defects actually reproduce, rely on existing parameterized coverage and the CI matrix for environments unavailable locally, disclose local-coverage gaps explicitly in every report, and never fabricate coverage by mocking internal components to force unreachable branches; when behavior is gated on a runtime precondition the test harness does not naturally satisfy, tests use a dedicated fixture that simulates that precondition so the intended branches are genuinely reachable, and the gate's own refusal branch is asserted as well. Crash-path tests inject the failure at a point where the raise can actually escape to the crash wrapper under test — code that deliberately absorbs exceptions and converts them into degraded per-item results is error-scenario territory instead — so the absorbing and propagating zones of an operation are mapped before choosing injection points. Test plans are complete and executable as written: every fixed-order validation branch gets a negative arm, every tri-state knob gets both of its arms, boundary transport rules such as empty collections passing through unchanged are pinned explicitly, and every asymmetry documented in a design's edge-case section is pinned by its own dedicated test with a full trace, because reaching the underlying rule only indirectly through other tests leaves a regression path and does not count as coverage. A boundary audit of the design's test stack identifies uncovered scenarios, and each gap is closed with tests that genuinely discriminate the behaviors at risk — multi-step versus single-step effects, correct configuration keys surfacing in errors, negative conflict and rejection paths, and accurate command and surface enumerations. Every test scenario in a design document carries all structurally required elements regardless of scenario kind — an explicit setup for invocation cases, a minimal trace for negative paths — and contains no half-finished draft fragments, so a test author can implement it directly. Each added case is a complete trace whose explanatory intermediate-step texts are part of the contract with the implementer and are verified against the real code and corrected where they diverge, even when the final assertions already pass, and every assertion line is syntactically correct, so the approved plan is executable as written rather than debugged downstream.

## Confirmed-problem gating, evidence-first explanation, and systemic-gap remediation

Surprising behavior is checked against intended semantics before being treated as a defect, since a legitimate empty or terminal state is not a bug to patch; the work item is the problem explicitly named by the user, never a task inferred from incidental ambient state. When the user answers an approval request with a question about the cause, the approval ask is paused: the mechanism is explained with concrete repository evidence and a comparison of the distinct states the old rule conflated, and only then are the options re-presented for decision — approval is never re-requested before the "why" is answered. When root-cause analysis establishes that no production defect exists, report the verdict with its full evidence trace and close only the genuine gap — the missing regression coverage for the untested scenario — leaving production code, specifications, and usage documents unchanged; never rework correct logic to appear productive, and never end the effort without protecting the untested seam. Specification precedence governs that verdict: when production code conforms to its governing specification, failing tests are themselves the defect — the tests are repaired and the production code, its specifications, and its usage contracts are left untouched, keeping the change fully backward compatible instead of weakening a manifest-defined contract to satisfy broken tests. When instead a defect's root cause is a gap in shared test infrastructure rather than an isolated mistake, the project explicitly prefers the complete remediation over the minimal patch: repair the individual defect, install a durable suite-wide guard that makes the entire failure class impossible to reintroduce, adapt the few cases that legitimately depended on the old behavior, and validate the result.

## Root-cause isolation, failure provenance, and fix locus

Every cause hypothesis is grounded in the real failure output and the runtime configuration of the environment that actually reported the problem, obtained from the reporter or the pipeline configuration; the failing configuration is never inferred from a local or unrelated environment, and the exact reported failures are reproduced before acting on any explanation. When multiple failure classes arrive together, reproduce and prove each cause separately against authoritative material — official documentation and the actual runtime sources — before fixing anything; never assume a single shared cause or diagnose solely from an aggregated CI report. Provenance, not surface signal, decides the outcome: an exception type alone never determines the result, so establish which component actually failed — for an import error, an absent target module means a quiet skip, while a present module failing through a broken transitive dependency is fatal — and pin the fatal path with a test that triggers the genuine transitive failure using a real broken package on disk, with no mocks inside business logic. The correction then lands at the single shared dependency that all affected cases pass through, never in outer orchestration configuration that only masks the symptom for one execution context, and never as per-case rewrites that work around the symptom.

## Isolated external verification environments

The project's own virtual environment is off-limits to verification work — never installed into, run from, or otherwise mutated when running tests or adding dependencies: any reproduction or check runs in a separate, disposable environment created outside the project tree, with the project's code attached via import path and the project installed into that environment. Dependencies are installed only into that external environment, never into the project's, and all test, lint, and CLI tooling run from that interpreter, so the repository never accumulates environment artifacts.

## Exhaustive and minimal change scoping

A fix's diff contains exactly what the approved task requires and nothing more: pre-existing unrelated uncommitted work is left untouched and explicitly out of scope, so the change set never mixes concerns. Within that approved scope execution is exhaustive — every verified review remark is applied regardless of severity, including test-gap additions and minor-severity precision fixes, never only a narrow factual subset — and affected chains are re-traced with lint re-run clean before completion is reported. When a design changes behavior, or removes or reshapes configuration types and keys, the affected-test inventory is compiled from an untruncated survey of the entire test corpus, unit and integration suites alike, and delivered as an explicit per-file disposition addendum — rewrite, fixture and assertion update, or deletion — with every affected test listed alongside its concrete new expectation instead of being left to the implementer's discretion, and a note on which incidental mentions remain harmless and are confirmed by a run, so the implementing agent executes the plan without further design decisions. A design that claims to be a complete implementation specification also enumerates how existing tests encoding a removed behavior are migrated — premises rewritten to the new mechanism, assertions extended with the new arguments, old-channel assertions inverted, and verbatim old-behavior tests replaced by their new-behavior counterparts — rather than leaving the migration to be improvised during implementation.

## Wording-first, contracted, and bijective status vocabulary

When a tabular display's semantics are reported as confusing, the remedy is wording, not layout: rename the column header or the value names and keep the table structure — rows, columns, and decorative elements — unchanged unless a structural change is explicitly requested. Status values exposed in machine-readable output are API surface and public contract, not table decoration: renaming any emitted value is a deliberate breaking change that must be disclosed in the change plan — stating exactly what changes and what stays identical — and explicitly approved by the user before implementation. The status vocabulary itself is bijective: each distinct underlying state maps to exactly one status term, and each term denotes exactly one state; no marker may duplicate a meaning another marker on the same view already carries, and no real state may lack its own value. Boundaries between adjacent states, including the ordering of the internal checks that distinguish them, are pinned by tests.

## Own-state ownership and directional divergence classification

What belongs to an entity is decided only by the entity's own direct facts, never by incidental associations. Indicators shown in aggregated views are derived from an entity's own direct state, never propagated from related or merged entities that merely carry its history. A branch bearing a topic's exact name is that topic's own branch, with no requirement that its tree carry the topic: deletion of an unpublished topic therefore cascades to that branch, a branchless topic reports an explicit nothing-to-delete outcome, and a topic without its own branch stays invisible on the board. The topic–base divergence marker is a directional, three-valued domain: containment is tested in both directions between the topic tip and the base projections, which distinguishes the topic-carries-the-base state from the base-carries-the-topic state, labels genuine divergence when neither direction holds, and yields an empty value when the base is unconfigured or unresolvable; a one-directional probe conflates distinct states and is itself the defect shape to eliminate. The delivered state is granted only when the topic reaches the base in full: tip containment is transitive, so it guarantees every commit is delivered, and a partially delivered topic must fail the probe and read as divergent — a boundary pinned by explicit matrix cases for full, partial, and one-sided delivery. Detection stays on cheap, read-only ancestry probes: states that ancestry cannot express, such as delivery without an ancestry link, deliberately read as divergent, the limitation is recorded as an explicit contract constraint, and content-based detection is kept out of display paths because its cost multiplies on every render.

## Explicit boundary-case specification and atomic conflict handling

An identified but unspecified failure scenario is defined explicitly in the design rather than left implicit: a clean error carrying the underlying reason, a stated end-state for already-completed work including documented exceptions to rollback, and retry responsibility assigned only to the operation that owns it. At runtime, a conflict signal from an underlying operation is honored on every code path, including optimized ones: the operation raises a clean error pointing to manual resolution and rolls back any already-written intermediate state, returning the system to its pre-operation state.

## Explicit decision-passing architecture

Orchestration decisions and exclusion lists travel as explicit parameters through every layer of the call chain, from the CLI entry point down to the innermost functions; a single designated environment variable is the only permitted environment read, and no parallel decision channel may coexist with the explicit one, so every behavioral choice is traceable to a value that was deliberately passed down rather than ambiently read.

## Boundary-consistent structural and sentinel-state validation

A merge path that accepts amended configuration values enforces the same structural rules the loading boundary already enforces — required strings must be non-blank, path values must be safe, blank normalizes to absent — raising hard errors that name the offending contributor and path instead of producing a configuration the loader itself would reject. When a contract makes input that is not representable in the target map structure a hard failure, guard with an explicit mapping-type check before merging, because standard merge operations accept any iterable of key-value pairs and silently coerce it into a valid-looking map; keep the structural check in its own error path so its failure format is not double-wrapped into the failure format of a different error class. Sentinel states stay distinct through these boundaries: an absent configuration section and an empty-but-present one are different inputs — only absence short-circuits preprocessing, while an empty section still performs cleanup and runs zero iterations — so gating logic must preserve the distinction rather than collapse it under a single truthiness check, and the asymmetry must stay pinned by tests even where downstream operations treat both states alike.

## Final-pass gating and reporting-signal invariants

In a multi-phase execution workflow, terminal whole-run decisions run as a single final pass after all contributing steps complete, never inside the apply loop: validity checks over composed configuration execute only after all winning amendments are applied, so outcomes never depend on amendment order, composition stays pure and all-or-nothing, and companion tests are expressed as order-independent. Every terminal decision keys on the composed result rather than on raw inputs: a contribution is committed iff the key-wise merged buffer is non-empty, not iff raw payloads were submitted, so a submission of only empty payloads stays a silent no-op — an edge pinned by a dedicated test driving a non-empty pending buffer that merges to empty, rather than relying on downstream filtering. Nothing-to-do decisions compare content-level results rather than identity-level handles, because distinct handles can encapsulate identical content after history-rewriting or merging operations. An output artifact may likewise be relocated to its completed location only when the last required phase exits successfully; a failure of any later phase must leave the artifact in place and propagate a non-zero exit, so the run stays resumable instead of losing its state. Reported outcomes are bound by fixed coincidences that hold on all paths: any item entering the changed set must flip the success flag and the exit signal to failure, and a stale verdict must always carry non-empty evidence, so every change to facts, reports, or projection logic must preserve these couplings rather than rebalance one signal in isolation.

## Degenerate-input and caller-owned hazard guards

Flows guard degenerate inputs at the very top, before validation, fact construction, and any event emission, honoring the rule that pre-launch failures fire no events; a path already guarded by an upstream launcher is still treated as reachable through direct invocation, and the guard mirrors existing degenerate-case precedents with a logged error and a nonzero exit instead of a traceback. When an underlying layer deliberately delegates a safety policy to its callers because its write mechanisms bypass the tool's own refusals, every operation in the layers above that can trigger the hazard enforces the guard itself, symmetrically across all commands: the precondition is checked first and fails with a clean, actionable error before any preliminary read or write.

## Exhaustive and internally consistent design claims

Cross-cutting error-handling claims enumerate documented exceptions instead of asserting absolutes: when platform documentation defines a fatal case that legitimately escapes unhandled, the design's statement carries that carve-out explicitly rather than resolving the internal contradiction by catching the exception and diverging from platform precedent. When a single document holds multiple mutually inconsistent statements about the same subject, the correction is applied to every statement at once and the affected paths are re-verified afterwards, so a literal reading of any one section remains executable-correct. A document never carries references that resolve to nothing: dangling markers are removed when the surrounding text is self-sufficient, and sections the document never contained are not reconstructed after the fact.

## Key-exact guidance and annotation alignment

Usage and practice documents name the exact configuration keys they describe, distinguishing which key each value is written to and where each value is sourced from, because loosely-named keys steer an implementer into writing values to the wrong place; the loose wording itself is replaced. A signature-level annotation likewise states exactly what its entity's requirements specify — every substitution token, transformation, and fallback — because implementers read signatures and annotations first.

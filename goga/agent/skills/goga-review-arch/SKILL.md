# Ревью архитектуры

## Цель

Проверяет план архитектуры (`docs/arch/<topic>.md`) на **полноту, корректность и внутреннюю согласованность** — убедиться, что все CODEMANIFEST и `.usages/` файлы спроектированы корректно и готовы к переходу к дизайну (`goga-design`).

Вы **верифицируете** план архитектуры, **сообщаете** о замечаниях и **исправляете** план при обнаружении проблем (с одобрения пользователя).

---

## Ключевой принцип

**Каждый CODEMANIFEST в плане должен быть синтаксически корректным, а все межъячеечные связи — согласованными.** План архитектуры описывает контракты для реализации. Если контракт содержит синтаксическую ошибку, неразрешимую ссылку или логическое противоречие — реализация по нему невозможна.

### Правило взаимодействия с пользователем

**Всегда предлагайте варианты ответа.** При обращении к пользователю за решением или подтверждением — всегда предоставляйте варианта ответа. Никогда не задавайте открытые вопросы без предлагаемых для выбора вариантов.

---

## Верифицируемый артефакт

- Файл плана архитектуры по адресу `docs/arch/<topic>.md` — план, проверяемый на корректность и согласованность

## Фазы

### Фаза 1: Загрузка контекста

1. Прочитайте план архитектуры из `docs/arch/<topic>.md`
2. Загрузите DSL спецификацию и принципы применения DSL:
   - Используйте **Skill tool** для вызова `goga-cell` — для получения справочника DSL
     (синтаксис сигнатур, правила Imports, Usages, Annotations, типы, мутации, встраивания, ограничения)
   - Используйте **Skill tool** для вызова `goga-cookbook` — для понимания принципов проектирования cell и CODEMANIFEST
     (когда использовать Entity vs Routine, когда применять мутации и встраивания, принципы написания usage файлов, гранулярность cell)
3. Используйте **Skill tool** для вызова `goga-codemanifest-base` — получите базовые usages и annotations проекта
4. Получите текущую схему проекта:
   - Выполните `docker run --rm -v .:/project -w /project qarium/goga:latest schema`, чтобы получить иерархию существующих cells
   - Это нужно для проверки: какие cells из плана создаются заново, а какие модифицируются
5. Прочитайте существующие CODEMANIFEST тех cells, которые план помечает как модифицируемые
6. Прочитайте существующие `.usages/` файлы модифицируемых cells

---

### Фаза 2: Проверка структуры плана

Проверьте, что план архитектуры содержит **все обязательные секции**:

1. **Порядок реализации** — cells упорядочены с указанием причины порядка
2. **Артефакты для каждой cell** — CODEMANIFEST и `.usages/` файлы
3. **Карта зависимостей** — ASCII-диаграмма или список связей между cells
4. **Чеклист верификации** — что проверить после реализации

Если любая секция отсутствует — зафиксируйте как **Критическое** замечание.
Если секция присутствует, но пуста или содержит плейсхолдеры (TBD, TODO) — зафиксируйте как **Высокое**.

#### Отсутствие кода реализации

План архитектуры содержит **только** артефакты CODEMANIFEST и `.usages/` файлов.
Если в плане обнаружены блоки кода реализации (Python, Go и т.д.) — зафиксируйте как **Критическое**.

---

### Фаза 3: Проверка каждого CODEMANIFEST в плане

Для каждого CODEMANIFEST, описанного в плане архитектуры, выполните следующие проверки.

#### Шаг 1. Синтаксическая корректность DSL

Используйте скилл `goga-cell` для справки по синтаксису.

- **Структура документа** — CODEMANIFEST содержит Header, Body, Footer в правильном порядке
- **Ключи** — регистр ключей соответствует спецификации (`Imports`, `Usages`, `Annotations`, `location`)
- **Сигнатуры** — формат `"()"` для конструкторов, сигнатуры методов и свойств соответствуют правилам DSL
- **Мутации** — формат `Object::Target` корректен
- **Встраивания** — формат `->Entity: {}` корректен
- **Ограничения location** — каждое значение `location` содержит только имя файла с расширением, без каталогов и без выхода за пределы текущего уровня

Если обнаружены синтаксические ошибки — зафиксируйте как **Критическое**.

#### Шаг 2. Полнота

- **Все типы присутствуют** — каждый тип, упомянутый в плане (в карте зависимостей, в Imports, в мутациях, во встраиваниях), имеет объявление в соответствующем CODEMANIFEST
- **Нет плейсхолдеров** — нет TBD, TODO, незавершённых описаний в CODEMANIFEST файлах плана
- **Footer** — Author, CreatedAt, Description присутствуют

Если типы отсутствуют — зафиксируйте как **Критическое**.
Если есть плейсхолдеры — зафиксируйте как **Высокое**.
Если Footer отсутствует — зафиксируйте как **Среднее**.

#### Шаг 3. Entity / Routine корректность

Используйте скилл `goga-cookbook` для понимания критериев.

- Каждый тип с `methods` и/или `properties` является Entity
- Каждый тип без `methods` и `properties` является Routine и не содержит этих секций
- Выбор Entity vs Routine обоснован (Entity — тип с состоянием и/или несколькими операциями, Routine — единственная операция)

Если классификация некорректна — зафиксируйте как **Высокое**.

#### Шаг 4. Использование Imports.Types

- Каждый импортированный тип (из `Imports.Types`) используется в теле документа:
  в сигнатурах, мутациях, встраиваниях или аннотациях текущего CODEMANIFEST

Если импортированный тип не используется — зафиксируйте как **Высокое**.

#### Шаг 5. Использование Usages и Imports.Usages

- Каждая объявленная в заголовке `Usages` практика упоминается хотя бы в одной аннотации
- Каждый импортированный usage (из `Imports.Usages`) упоминается хотя бы в одной аннотации

Если практика не упоминается — зафиксируйте как **Высокое**.

#### Шаг 6. Разрешимость ссылок в аннотациях

- Каждая ссылка в обратных кавычках внутри аннотаций разрешима в контексте текущего CODEMANIFEST:
  переменная из сигнатуры, тип из Imports или объявленный в документе, практика из Usages или Imports

Если ссылка неразрешима — зафиксируйте как **Высокое**.

#### Шаг 7. Мутации и встраивания

- Каждый встраиваемый тип (через `->`) доступен через `Imports`
- Базовые типы в мутациях (`Object::Target`) доступны: импортированы через `Imports` или объявлены в текущем CODEMANIFEST

Если типы недоступны — зафиксируйте как **Критическое** (реализация невозможна).

#### Шаг 8. Базовые usages и annotations

- Если скилл `goga-codemanifest-base` вернул базовые usages — каждая базовая практика включена в директиву `Usages` всех CODEMANIFEST и на неё есть ссылка хотя бы в одной аннотации
- Если скилл `goga-codemanifest-base` вернул базовые annotations — базовые annotations включены в директиву `Annotations` всех CODEMANIFEST

Если базовые практики или инструкции отсутствуют — зафиксируйте как **Высокое**.

#### Шаг 9. Usages внешних библиотек

Для каждого CODEMANIFEST в плане:

- Если в аннотациях или сигнатурах упоминается внешняя библиотека/технология, для которой в проекте существует usage-файл в `.goga/usages/cooks/` — этот файл должен быть подключён через директиву `Usages`
- Если библиотека используется, но usage-файла не существует — зафиксируйте как замечание

Если библиотечный usage-файл существует, но не подключён — зафиксируйте как **Высокое**.

---

### Фаза 4: Межъячеечная согласованность

#### Шаг 1. Корректность Imports

Для каждого CODEMANIFEST в плане:

- **Существование cell-источника** — каждый `Imports.Types` или `Imports.Usages` ссылается на cell, которая существует либо в текущей схеме проекта, либо в самом плане архитектуры
- **Существование типа в cell-источнике** — импортированный тип действительно объявлен в указанной cell (проверьте CODEMANIFEST этой cell в плане или в проекте)

Если cell-источник не существует — зафиксируйте как **Критическое**.
Если тип не найден в cell-источнике — зафиксируйте как **Критическое**.

#### Шаг 2. Отсутствие перекрёстных импортов

- Если cell A импортирует из cell B, то cell B не импортирует из cell A

Если обнаружены перекрёстные импорты — зафиксируйте как **Критическое**.

#### Шаг 3. Согласованность типов на границах

Для каждой связи между cells (через Imports):

- Тип, который cell A экспортирует (объявляет в своём CODEMANIFEST), совпадает с тем, что cell B импортирует (имя, сигнатура)
- Если cell B использует мутацию или встраивание типа из cell A — базовый тип корректен

Если типы не совпадают — зафиксируйте как **Критическое**.

#### Шаг 4. Карта зависимостей

- Карта зависимостей в плане точно отражает все Imports-связи между cells
- Нет связей, указанных в карте, но отсутствующих в CODEMANIFEST
- Нет связей, присутствующих в CODEMANIFEST, но отсутствующих в карте

Если карта не согласована — зафиксируйте как **Высокое**.

#### Шаг 5. Корректность путей cells

Для каждой новой cell в плане (не модифицируемой, а создаваемой заново):

- Путь к cell соответствует конвенциям проекта, наблюдаемым в schema (структура каталогов, именование)
- Путь к cell совпадает с путями, указанными в `Imports.From` других cells которые ее импортируют

Если путь не соответствует конвенциям проекта — зафиксируйте как **Среднее**.
Если путь в плане не совпадает с `Imports.From` — зафиксируйте как **Высокое**.

---

### Фаза 5: Порядок реализации

#### Шаг 1. Корректность порядка

- Каждая cell создаётся **после** всех cells, от которых она зависит (указанных в её `Imports`)
- Порядок «от листьев к корню» соблюдён: cells без Imports идут первыми

Если порядок нарушен — зафиксируйте как **Критическое** (реализация будет заблокирована).

#### Шаг 2. Обоснованность причин порядка

- Для каждой cell указана причина порядка (например: «не имеет Imports», «зависит от cell X»)
- Причина соответствует фактическим Imports

Если причина не указана — зафиксируйте как **Среднее**.
Если причина не соответствует Imports — зафиксируйте как **Высокое**.

---

### Фаза 6: Проверка .usages/ файлов

Для каждого `.usages/` файла, описанного в плане:

#### Шаг 1. Существование и полнота

- Для каждой cell в плане описаны `.usages/` файлы, которые нужно создать или модифицировать
- Содержимое `.usages/` файлов приведено полностью (а не как ссылка или плейсхолдер)

Если содержимое отсутствует — зафиксируйте как **Высокое**.

#### Шаг 2. Качество .usages/ файлов

Используйте скилл `goga-cookbook` для проверки принципов написания usage файлов.

- Каждая практика описывает использование API cell (а не внутреннюю реализацию)
- Содержание достаточно детально для потребителей
- Функциональные категории `.usages/` чётко определены и не пересекаются

Если качество недостаточно — зафиксируйте как **Среднее**.

#### Шаг 3. Связь с CODEMANIFEST

`.usages/` файлы описывают практики использования API cell-провайдера. Поэтому потребитель cell-провайдера должен ссылаться на эти практики в своём CODEMANIFEST.

- Для каждого `.usages/` файла, создаваемого cell-провайдером, существует потребитель, который подключает этот usage через `Imports.Usages`
- Каждый подключённый usage упоминается хотя бы в одной аннотации CODEMANIFEST потребителя
- Если consumer не подключил usage file провайдера — он не сможет корректно использовать API этой cell

Если потребитель не подключил usage провайдера — зафиксируйте как **Высокое**.
Если подключённый usage не упоминается в аннотациях — зафиксируйте как **Среднее**.

---

### Фаза 7: Согласованность с существующей архитектурой

Для cells, которые план помечает как модифицируемые (уже существуют в схеме проекта):

#### Шаг 1. Корректность модификации

- План явно указывает, какие cells модифицируются, а какие создаются заново
- Для модифицируемых cells план содержит diff: что добавить, что изменить, что удалить
- Модификации не ломают существующие контракты, на которые ссылаются другие cells

Если модификация не описана как diff — зафиксируйте как **Высокое**.
Если модификация ломает существующие контракты — зафиксируйте как **Критическое**.

#### Шаг 2. Влияние на зависимые cells

- Проверьте, не затрагивают ли изменения в плане cells, не упомянутые в плане, но зависящие от модифицируемых cells
- Используйте `--depends-on <cell_path>` для поиска зависимых ячеек

Если есть незатронутые, но влияющие cells — зафиксируйте как **Высокое**.

### Фаза 8: Отчёт и исправление замечаний (интерактивно)

Соберите все замечания из Фаз 2–7 перед их представлением. Отсортируйте по критичности: Критические → Высокие → Средние.

Представляйте замечания **по одному**. Для каждого замечания:

#### Шаг 1. Покажите замечание

Представьте одно замечание с:

- **Критичность** (Критическая / Высокая / Средняя)
- **Местоположение** — точная ссылка на секцию плана архитектуры или конкретный CODEMANIFEST
- **Что не так** — ясное описание проблемы
- **Предлагаемое исправление** — точное необходимое изменение, а не расплывчатый совет

#### Шаг 2. Запросите решение у пользователя

Используйте AskUserQuestion с вариантами:

1. **Применить предложенное исправление** — немедленно применить исправление к плану архитектуры
2. **Предложить альтернативу** — пользователь описывает другой подход к исправлению

#### Шаг 3. Примените решение

- **Применить предложенное исправление**: обновите план архитектуры, затем перепроверьте, что исправление не вносит новых проблем (повторно выполните релевантные проверки). Кратко сообщите результат перепроверки.
- **Пропустить**: зафиксируйте замечание как «пропущенное» и продолжите.
- **Предложить альтернативу**: обсудите альтернативу с пользователем, согласуйте исправление, примените его, перепроверьте.

#### Шаг 4. Переход к следующему замечанию

Повторите с Шага 1 для следующего замечания. Показывайте краткий счётчик: «Замечание 3 из 12».

После обработки всех замечаний покажите итоги:

- **Исправлено**: N замечаний (список по критичности)
- **Пропущено**: N замечаний (список по критичности)
- **Статус плана архитектуры**: обновлён / без изменений

- Обновлённый файл плана архитектуры (если были применены исправления)

## Финальная самопроверка

Перед завершением проверьте:

1. Была ли DSL спецификация загружена через скиллы `goga-cell` и `goga-cookbook` перед ревью?
2. Были ли получены базовые usages и annotations через скилл `goga-codemanifest-base`?
3. Была ли загружена текущая схема проекта?
4. Была ли проверена структура плана (все 4 обязательные секции)?
5. Был ли каждый CODEMANIFEST проверен на синтаксис DSL, полноту, Entity/Routine, Imports, Usages, аннотации, мутации, встраивания?
6. Была ли проверена межъячеечная согласованность (Imports, перекрёстные импорты, типы на границах, карта зависимостей)?
7. Был ли проверен порядок реализации (от листьев к корню)?
8. Были ли проверены `.usages/` файлы (полнота, качество, связь с CODEMANIFEST потребителей)?
9. Была ли проверена согласованность с существующей архитектурой (модификации, влияние на зависимые cells)?
10. Было ли каждое замечание представлено по одному с решением об исправлении?
11. Были ли одобренные исправления применены и перепроверены?
12. Были ли предоставлены итоги исправленных/пропущенных замечаний?

Если хотя бы один ответ «нет» — завершите недостающую верификацию перед возвратом.
